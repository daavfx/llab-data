# PQ2_0 AVX2 vec_dot candidate - rationale

Target: Ryzen 5 5600G (Zen 3: AVX2 + FMA3, NO AVX512, NO AVX-VNNI). Today it falls
into the scalar `#else` fallback of `ggml_vec_dot_pq2_0_q8_0` because the fast
branch requires `__AVX512VNNI__ + __AVX512VL__` or `__AVXVNNI__`.

Patch site: `ggml/src/ggml-cpu/arch/x86/quants.c`, function
`ggml_vec_dot_pq2_0_q8_0` (starts line 561). The diff inserts an
`#elif defined(__AVX2__)` branch between the existing VNNI branch and the
scalar `#else`. Confirmed in `arch-fallback.h` (line ~195, AVX2 guard section)
that AVX2 builds currently alias `ggml_vec_dot_pq2_0_q8_0` to the generic, so
adding a real AVX2 branch in the x86 file is exactly the intended fix point.

## (a) Byte layout of block_pq2_0 (ggml-common.h lines 200-207)

```c
#define QK_PQ2_0 128
typedef struct {
    ggml_half d;                    // one fp16 scale per 128 weights
    uint8_t   qs[QK_PQ2_0 / 4];     // 32 bytes, 2 bits per element
} block_pq2_0;                      // sizeof = 2 + 32 = 34
```

Same 2-bit codec as Q2_0 but group-128 instead of group-32. Codes c in
{0,1,2,3} map to values (c-1) in {-1,0,1,2} ("2.5 bpw ternary pair"). Packing:
block byte b holds weights 4b..4b+3, weight j uses bits (2*(j%4))..(2*(j%4)+1)
of byte j/4. The counterpart y rows are block_q8_0: ggml_half d + 32 int8
(qs), values in [-127,127]. One PQ2_0 block pairs with 4 q8_0 blocks:
sub-block k (32 weights) uses `x[i].qs[k*8 .. k*8+7]` and `y[i*4+k]`.

## (b) Generic (scalar) loop, op by op

Per block i (nb blocks), per sub-block k in 0..3:
1. Load q8 scale d1 = fp32(y[i*4+k].d).
2. For each of 8 bytes: extract four 2-bit codes via `(byte>>s)&3` (s=0,2,4,6),
   subtract 1, multiply by qy[b*4+j], accumulate into int `sumi_block`
   (128 scalar int multiply-adds per sub-block).
3. `sumi += d1 * sumi_block` (float).
Per block: `sumf += d0 * sumi`, d0 = fp32(x[i].d). Final `*s = sumf`.

Cost: ~128 scalar imul+iadd plus 8 shifts/ands per sub-block = ~512 int ops +
loads per 34-byte block. This is the 0.4 t/s path.

## (c) AVX2 kernel mapping

Identical unpack as the existing VNNI branch (every intrinsic in that prologue
is already pure AVX2 - the VNNI part was only the dpbusd at the end):

Per sub-block:
1. `qy = _mm256_loadu_si256(yb->qs)` - all 32 int8 activations at once.
2. `src = _mm_loadl_epi64(&x[i].qs[k*8])` - 8 packed bytes.
3. `_mm_shuffle_epi8(src, idxlo/idxhi)` - broadcast each byte to 4 lanes
   (idxlo: bytes 0-3 x4 each; idxhi: bytes 4-7 x4 each);
   `MM256_SET_M128I` joins them into 32 bytes, one per code position.
   (MM256_SET_M128I is the file's portable `_mm256_set_m128i`, line 26.)
4. `_mm256_cvtepu8_epi16` x2, `_mm256_mullo_epi16(mul)` with
   mul=(64,16,4,1)x4 = shift left by (6-2c), `_mm256_srli_epi16(6)`,
   `_mm256_and_si256(three=3)` -> each 16-bit lane = the 2-bit code.
   Position j in the register corresponds to (byte j/4, slot j%4) with
   multiplier selecting shift amount - verified algebra: (b*64>>6)&3 = b&3,
   (b*16>>6)&3 = (b>>2)&3, (b*4>>6)&3 = (b>>4)&3, (b*1>>6)&3 = (b>>6)&3.
5. `_mm256_packus_epi16(r0, r1)` + `_mm256_permute4x64_epi64(0xD8)` restores
   sequential order: 32 codes as unsigned int8, aligned 1:1 with qy.
6. Replace dpbusd with the classic AVX2 pair:
   - `dp = hsum_i32_8(madd_epi16(maddubs_epi16(codes, qy), ones16))`
     = sum_j c_j * qy_j   (maddubs: u8*s8 -> s16 pairs, madd: pairs -> s32)
   - `sy = hsum_i32_8(madd_epi16(maddubs_epi16(ones8, qy), ones16))`
     = sum_j qy_j
7. `sumi += d1 * (float)(dp - sy)` - bit-identical expression to the VNNI
   branch, because (c-1)*q = c*q - q.

No tail handling needed: `assert(n % qk == 0)` and both existing paths loop
over full blocks only; the AVX2 branch copies that structure exactly.

## (d) Why 5-10x

Per sub-block the generic loop executes ~512 scalar int ops. The AVX2 kernel
executes ~15 SIMD instructions (load, 2 shuffles, combine, 2 cvt, 2 mullo,
2 srli, 2 and, pack, permute, 2 maddubs, 2 madd, 2 hsum) for the same 128
MACs - a ~30x op-count reduction in the hot part; net of hsum (3-level, 2x per
sub-block) and scale handling, realistic wall speedup is 5-10x
(Zen 3: 2x256-bit FMA/PMADDWD pipes, maddubs = 1 uop / 3c lat / 0.5c tput).
A further ~2x is available later by hoisting `sy` across sub-blocks and by
batching all 4 sub-blocks with fp accumulators, but that changes the FP
accumulation order and is deliberately left out to keep the patch
obviously correct.

## (e) Correctness argument

- Integer exactness: maddubs unsigned arg codes in [0,3], signed qy in
  [-127,127] => products in [-381,381], pairwise sum in [-762,762], fits int16
  with no saturation (saturation range is [-32768,32767]). madd_epi16 with 1
  sums pairs of those into int32 exactly. dp, sy, dp-sy are exact integers,
  equal to the VNNI dpbusd results (dpbusd saturates only at int32 accumulate
  - same here, unreachable: |sum| <= 128*381 < 2^16).
- Float order: identical to the VNNI branch - int difference first, then
  d1*(int), summed over k into float sumi, then d0*sumi into sumf. The scalar
  path computes the same int per sub-block too (int add is associative and
  exact), so all three paths agree bit-for-bit.
- Unpack: step-by-step byte/shift algebra in (c-4) matches
  `((byte>>s)&3)` for s=0,2,4,6; order after packus+permute4x64(0xD8) was
  validated in the shipped VNNI code, which uses the identical sequence.
- Registers/intrinsics: SSSE3 (shuffle_epi8, maddubs), AVX (cvtepu8_epi16 on
  ymm is AVX2), AVX2 only for the rest. No AVX512, no VNNI, no GFNI.

## (f) Test plan

1. Apply: `git apply pq2_0_avx2_candidate.diff` in the prism repo.
2. Cross-check harness (no new tests/* file - reuse existing):
   - Build once with `-mavx2 -mno-avx512f` (forces our branch) and once with
     `-mno-avx2` (forces scalar `#else`).
   - Run `tests/test-quantize-fns` and the vec_dot path of
     `test-backend-ops` (PQ2_0 is already in its type list, lines 8354+).
     test-backend-ops compares CPU backend against itself, so primary gate is:
3. Bit-exact check: tiny standalone driver calling
   `ggml_vec_dot_pq2_0_q8_0` vs `ggml_vec_dot_pq2_0_q8_0_generic` (exported via
   the generic symbol) over ~1000 randomized rows (n = 128*m, m up to 32),
   including adversarial extremes (qy = +/-127, codes all 0 / all 3).
   Require `avx2_result == generic_result` bitwise (both are the same int math
   wrapped in the same float accumulation order, so exact equality is the
   expected outcome; report max |diff| as well in case a compiler reorders FP).
4. Then re-enable the bench (`llama-bench` with the PQ2_0 gguf on the 5600G)
   after the overnight queue drains.

## Note on an alternative (documented, not chosen)

The `sy` term (sum of qy per q8_0 block) is activation-only. A future
follow-up could precompute all 4 sy values per block with one 128-byte wide
pass or keep a running fp accumulator like the q1_0 AVX2 kernel does. That
trades bit-exactness vs the scalar path for another ~1.3-2x. Flag for
PRISM_TEAM review; not part of this candidate.
